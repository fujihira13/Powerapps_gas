## 結論と対象

承認済みの4画面（UI-20260924-01）を、件別の保存・処理・Excel実反映・担当者確認・レビューを追えるPower AppsとPower Automateの作品として実装する。先にT-001～T-003で技術方式を小さく検証し、T-004でデータと回復方法を設計し、T-005で未決定の画面仕様を確定し、T-006で架空データと保存先を準備する。その結果を反映して本計画と`docs/CHECKS.md`を確定した後、T-008～T-012へ進む。

本書は、現時点で決められる実装順序と検証条件を提示する。保存先、テーブル／リストの構造、フローの具体的な構成、制限値、費用、外部環境の識別子は未確定であり、実施前に追記する。T-001～T-006の検証・設計・準備を省いて実装へ進む計画ではない。

## 根拠・境界

- 要件：`docs/REQUIREMENTS.md`のREQ-01～REQ-06、C01～C09。同資料の「技術上の規律」TR-01～TR-06は承認待ちの草案。`docs/TASKS.md`のT-001～T-012を進行記録とする。要件整理中の未承認表記は当時の履歴として残している。
- 画面：`docs/ui/rules.md`とSCR-01～SCR-04の個別仕様。4画面構成、記載された文言・選択値・操作・遷移はUI-20260924-01として承認済み。未決定欄は画像や推測から埋めない。
- 対象外：実務ログ・顧客情報、バッチ実行、サーバーからのログ取得、Excel関数、別アカウント間の権限制御、メール／Teams通知、一般公開。1アカウントで二役を実演し、独立した別人のレビューと表現しない。
- 変更対象：Power Appsの4画面、Power Automateの件別処理、採用が決まった架空データの保存先・Excelひな形、再現用データ、確認資料。現時点のリポジトリにアプリ／フローのソースはなく、具体的なファイルパスは未設定。エクスポート方式が決まった後に対象パスを記入し、既存変更を保護する。

## 設計・実装で確定する項目

1. **件の識別と状態（TR-01～TR-03）**：T-004で識別キー、状態記録先、Excel参照、重複・再実行の判定方法を決める。守る条件は`docs/REQUIREMENTS.md`の「技術上の規律」を参照する。
2. **反映確認と回復（TR-02・TR-03）**：T-002～T-004で実内容の確認方法、結果不明時の確認手順、再実行条件を決める。
3. **入力と遷移**：ログ形式・件数・サイズ、実行回と日付の形式、0件、保存結果不明、画面再表示、未保存入力、読出／保存失敗、レビュー依頼可能条件、差し戻し後の修正範囲を個別画面仕様へ記録する。
4. **保存先と費用**：本人のPower PlatformとMicrosoft 365環境で、採用コネクター、権利、料金、データの保管先と保持・初期化方法を確認する。候補のSharePoint／Excel Online (Business)を採用確定と扱わない。

## 検証・証拠・戻し方

- 検証の詳細は`docs/CHECKS.md`の草案に記す。保存、日付判定、状態遷移、重複防止、再実行、判断とレビューの記録は、可能なら期待結果から自動試験を先に作る。Power Platform上で自動化できない部分は架空データによる手動再現とExcel実内容の照合を用い、理由を記録する。
- 画面ごとにPCブラウザで正確な文言、状態、欠け・重なり、画面外へのはみ出し、操作を確認する。共通部品の変更は4画面を再確認する。受付の参考画像は設計の出発点であり、基準画像は実画面のユーザー受入後に作成する。
- 条件IDごとに対象アプリ／フローの版、OS・ブラウザ、操作、期待結果、実結果、画面とExcelの証拠を残す。実装担当の自己確認の後にテスト担当と独立レビュー担当が確認し、正式な不合格は同一タスクで3回に達したら停止する。
- 失敗時は対象件の状態と既存証跡を確認し、再実行可能条件が成立しなければ処理を止める。開発中の変更は直前のエクスポート／版へ戻せる手順をT-007確定時に記入する。架空データの初期化や削除は対象と復元可否を確認してから行い、過去証跡を消して合格扱いにしない。
