開始前に保存済みの件を取り消した後、同じ4項目でやり直す場合は、2026-09-25のユーザー回答に従い**元の件を再開してログを差し替える**。同じ件IDと4項目を使い、2行目・2冊目のExcelを作らない。差し替え前の添付が残る場合も、処理に使うログを1件に確定できるまで開始しない。新旧ログの入れ替え手順、失敗・結果不明時の旧ログの扱い、正確な画面操作はT-004・T-005で設計する。実際の外部ファイル削除や上書きはT-007で対象・復元方法と実行範囲を決めるまで行わない。

差し替え時は開始前取消を保存先で確認してから、元の件IDへ新ログを保存する候補とする。旧ログをすぐ削除・上書きせず、新ログの本文を読み戻した後に、処理に使う添付IDを新ログへ切り替える案なら旧ログを守りやすい。ただし現在の添付機能でこの順序が可能かは未検証。Canvas Authoring MCPで現行アプリのデータ接続と添付コントロールを読み取ったところ、接続は書込可能なDataverseで、添付コントロールには追加・削除の入力がある。一方、現行`log-evidence-app/Screen1.pa.yaml`のフォームは`FormMode.New`と`NewForm`だけを使い、保存済み行の編集・添付差し替えは実装も検証もしていない。新ログの保存応答が失敗・不明なら、元の件と添付を読み直して「旧ログのみ／新ログのみ／両方／添付なし／読出不能」を区別する。**応答不明を取消状態が維持された証拠とは扱わない。**有効添付の切替応答まで不明なら、件の状態と有効添付IDを再照会し、差し替え前／差し替え済み／判定不能を確定するまで画面で開始を受け付けない。差し替え済みでも処理開始は別操作として残す。旧ログのみ、添付なし、読出不能などの未解決時は自動で再送・削除・処理開始しない。Dataverse添付の具体的な保存順序と戻し方をT-004・T-007で確認し、旧ログの保持まで実証したとは扱わない。

安全な失敗件の再実行は、初回の「開始受付済み」を維持したまま、**新しい処理試行**として受け付ける。件ID・4項目・開始要求ID・固定した添付と転記先・Excel名は変えない。初回と各再試行に別の試行IDと単調増加する試行番号を割り当てる。前のフロー実行が終端状態で、同じ件の実行が他になく、Excelのコピー／書込が未着手または副作用を残さず確定失敗し、固定先に対象Excelが存在しないと確認できた場合だけ、件表の現在の試行ID・試行番号・失敗状態・版を条件に次の試行へ一度だけ更新する。コピーや書込の結果が不明、外部処理の遅延が残る、対象Excelの不存在を確定できない場合は再試行不可とする。再試行の受付応答が不明なら、要求した試行IDと件表の現在の試行を照会して確定するまで二度目の要求を送らない。旧試行と新試行のフローは、外部副作用の前と状態更新前に自分の試行IDが現在値と一致するか確かめ、状態更新は試行ID・版を条件に行う。遅れて届いた旧試行の成功・失敗・タイムアウトは新試行の状態や確認済みの実反映を上書きできない。初回開始受付を再度行う操作は常に拒否する。実際のフロー実行終了・外部処理の未着手／確定失敗・条件付き更新を確認する手段はT-007で定め、確証がなければ確認待ちに留める。

**C04との仕様差異と解決（2026-09-25のユーザー回答）**：従来の「失敗した件を修正して再実行」はログや4項目の修正も含むように読め、開始後固定と衝突していた。ユーザーは、処理開始後のログ・4項目は変えず、再実行前には処理の失敗原因だけを直す案を選択した。ログ・4項目の誤りは開始前に修正する。`docs/REQUIREMENTS.md`のC04をこの意味へ改め、開始後の再試行は上記の固定値と安全条件を守る。
