# 作業の進め方

## この文書の使い方

- AGENTS.mdを基本方針と参照案内、この文書を詳細手順として併用する。毎回全文を読むのではなく、今回の依頼に関係する節だけを読む。承認済みの判断と適用済みの手順は引き継ぐ。
- 認識合わせ・計画では「認識合わせと計画」「工程ごとの進行」、調査・要件整理・設計・実装では「役割分担と引き継ぎ」「評価・修正・停止」「記録・完了・再開」の該当部分を参照する。
- 外部操作を伴う場合は「外部操作を行う場合」、個人情報・認証情報を扱う場合は「データ・認証情報を扱う場合」も参照する。
- この文書中のREQUIREMENTS.md、TASKS.md、CHECKS.mdは、それぞれdocs/REQUIREMENTS.md、docs/TASKS.md、docs/CHECKS.mdを指す。AGENTS.mdはプロジェクト直下を指す。
- この文書は進行ルールであり、担当の割り当てや実施結果の記録ではない。作成しただけでサブエージェントの起動、レビュー担当の確保、テスト環境の準備、テストの実施、アプリの調査・実装を済ませたと扱わない。必要な資料・担当・環境の有無と実施状況は、各作業時に確認して記録する。

## 認識合わせと計画

- 新しい依頼では、達成したい結果、変更範囲、変更しない範囲、未決定、完成条件を整理し、認識を合わせる。承認済みの判断は引き継ぐ。
- ユーザー本人の操作を案内するときは、目的、全体の流れ、今行う一操作、触らない項目、成功時の表示を示す。
- 実装前に目的、対象ファイル、変更範囲、利用者から見た動作、順序、検証方法、費用・外部通信、失敗時の戻し方を提示して承認を得る。
- 説明した具体案への「その内容で修正して」は承認と扱い、同じ承認を繰り返し求めない。承認済み計画が複数タスクを明示的に含む場合はその範囲を引き継ぐ。
- 指定外の改善、機能追加、仕様変更、大規模整理、依存関係の更新を混ぜない。必要なら理由と影響を説明し、追加承認を待つ。
- 着手前に既存の変更を確認し、ユーザーや別担当の変更を上書きしない。競合時は担当を特定して調整する。
- 承認範囲内の不具合は修正・再検証する。合格条件や公開範囲を勝手に変えない。
- 範囲外のバグ・懸念も報告するが、無断で修正しない。今回の完了判断への影響を明示する。

## 役割分担と引き継ぎ

- オーケストレーターをユーザーとの窓口とし、調査・実装・テスト・レビュー担当へ必要な作業を割り振る。
- 実装・テスト実行・独立したレビューには、Codexの設定ファイルで定めた担当とモデル・推論強度を使う。この文書に具体的なモデル名を固定せず、起動時の指定やプロジェクト設定が共通設定を上書きしていないか確認する。確認できない値は未確認とし、利用できない担当やモデルを黙って代替しない。
- 利用量を抑える実装担当には、対象範囲、入出力、異常時の動き、変更禁止箇所、完成条件、確認方法が明確な作業を渡す。必要な資料の該当部分を示し、判断に不要な会話履歴や同じ調査をむやみに重複させない。
- テストの実行・結果整理と、テスト観点の設計・不足の判断を分ける。テスト実行担当には決まった手順と期待結果を渡し、観点の不足やテスト自体の妥当性は統括・設計担当と独立したレビュー担当が確認する。
- 仕様の曖昧さ、担当範囲を超える変更、同じ原因での修正の繰り返しが見つかったら、正式な不合格3回を待たずに統括へ戻す。統括は原因を整理し、作業の分割、推論強度や担当モデルの変更の必要性を判断する。承認済みのモデル運用の範囲を超える変更はユーザーへ確認し、共通設定は個別タスクの都合で無断変更しない。担当・モデルを変更しても不合格履歴と停止条件は引き継ぐ。
- 役割分担とレビューは調査・要件定義から適用する。引き継ぎには目的、対象範囲、確認する条件、利用可能な資料、担当範囲、変更禁止箇所、確認方法、評価履歴を含める。要件ID・タスクID・承認済み計画・画面仕様・参考画像等は、その工程で作成済みのものを渡す。実装・レビュー担当には対象の仕様と`REQUIREMENTS.md`の技術上の規律をセットで渡し、対応する検査項目は`CHECKS.md`を参照させる。未作成・未承認の資料を推測で補わない。
- 調査や要件整理を含め、成果物を作る担当とレビュー担当を分ける。調査は根拠と調査範囲、要件はユーザーの意図・矛盾・未決定、実装は差分・実動作・テスト結果を確認する。自己申告だけで合格にしない。担当分けが利用できない場合は報告し、代替方法への判断を得る。
- 共通ファイルを複数担当が同時に変更しない。独立している調査は並行できる。機能の同時実装は依存関係と統合責任者を明確にした場合だけ行う。
- 各担当は製品判断を独断で確定せず、オーケストレーターへ質問を返す。
- レビュー合格後もオーケストレーターが全体の整合性と未解決事項を確認する。レビュー合格だけで公開しない。
- UIの実装・変更前に、対象の画面仕様、参考画像、承認済みの実装画面があればその基準画像を確認する。文言・機能・操作・状態・遷移は承認済み仕様に従い、仕様にない説明文・見出し・ボタンを独断で追加しない。動的な文言は表示元と表示条件を仕様で定める。仕様と共通ルールが矛盾する場合は統括へ戻し、画像から推測して解決しない。
- 主要画面の新規作成や構成・導線の大きな変更では、設計を左右する技術上の制約を先に調べ、仮データで動く対象画面をユーザーが確認してから本処理・保存と結合する。モックの受入は見た目と仮の操作の受入であり、実機能や保存の合格ではない。小さな文言・余白の変更に毎回モック工程を追加しない。
- 初回の画面作成では、仕様で改善を認めた余白・整列・視認性などだけを調整する。実装画面の受入後は、機能追加の依頼に無関係な見た目の改善を混ぜない。仕様違反の修正と任意のデザイン改善を分け、後者は別の提案として扱う。
- UI変更後は実際に対象画面を表示し、正確な文言、不要な表示、重なり・欠け・画面外へのはみ出しと操作を確認する。共通部品の変更が影響する既存画面も対象とする。実装担当の自己申告だけでなく、テスト・レビュー担当が画面と結果を確認し、承認範囲内の不具合を修正・再確認してからユーザーへ提示する。実行できない確認は未確認として示す。
- 参考画像はデザインの出発点、ユーザーが受け入れた実装画面の画像は回帰確認の基準として区別する。基準画像には対象版・画面・状態・表示条件・承認時点をひも付ける。画像比較だけで動作を合格にせず、テストを通すために基準画像を自動更新しない。正式に承認された変更と検証結果を根拠に更新し、変更前も追跡できるようにする。
- スキルやツール・MCP・外部サイトの不調、接続失敗、権限不足、未実施の担当確認を隠さない。架空の担当・確認結果を報告しない。
- 必要なスキル・MCP・外部サイト・資料を利用できないときは、何を確認・実行する予定だったか、対象の機能やURL（秘密情報を除く）、失敗内容、試した再確認、未確認の範囲、成果物と完成条件への影響を記録・報告する。承認済みの範囲で別の手段を試せる場合は、その手段で何を確認できたかと限界も示す。開けていないページを読んだことにせず、検索結果の断片・古い資料・記憶を最新の一次情報として扱わない。必須の根拠や確認条件を満たせない場合は未確認として該当作業を止め、推奨する次の対応を示す。

## 評価・修正・停止

- 合格条件は作業開始前にユーザーと合意し、条件IDごとに合格・不合格・未確認・対象外と証拠を記録する。条件IDが未作成の場合は未作成と明記し、どの条件の判定か分かる形でチャットに記録して、資料・ID作成時に転記する。対象外には理由を残す。
- 必須条件は全項目合格が必要。点数で重大な問題や不合格を相殺しない。未確認のまま完了・公開しない。
- 全工程で、確認条件の合意→担当の作業・自己確認→工程に応じた検証→レビュー→不足の修正・再調査→再確認を行う。検証方法は変更内容と影響に応じて作業前に決める。実装では自動テスト・操作確認の必要性と対象を示し、実施しない方法がある場合は理由と代替確認を計画に記載して承認を得る。作業後に都合よく検証を省略しない。影響する合格済み項目も再確認する。
- 同じタスクの初回評価を含め、正式な不合格判定3回で停止する。初回不合格→修正→2回目不合格→修正→3回目不合格→ユーザーへ報告。
- 一回の正式評価は、合意した確認条件に対し、調査根拠・仕様の照合・テスト結果等を集約したレビュー担当の判定。通常の質問、ユーザーの回答待ち、作業途中の自己確認、個別テスト失敗を別回に数えない。ツール障害等で評価できない場合は未確認として直ちに報告し、評価回数で無理に進めない。
- 合格後に統合時の不具合が見つかった場合も記録する。同じタスクを再開するなら過去の不合格履歴を保持する。
- 名前変更、担当変更、チャット変更で回数をリセットしない。停止後の再開条件・追加試行の上限はユーザーと決める。
- 3回を待たず、認識のずれ、仕様変更、範囲拡大、追加費用、確認不能、データ消失の懸念があれば該当作業を止める。
- 停止報告は未達条件、試した修正、原因の事実と仮説、影響、推奨対応、ユーザーに必要な判断を含める。
- 合格のためにテストを削除・無効化したり、型チェック・Lint・合格条件を緩めたりしない。
- バグ修正や、自動で期待動作を判定できる保存・計算・入力制限・権限等の処理は、原則としてテスト駆動開発（TDD）を使う。完成条件からテストを先に作り、想定した理由で失敗することを実行で確認してから実装し、成功後に必要なコード整理と再検証を行う。テストが要件を正しく表しているかもレビューする。見た目の調整・文書変更・探索的な試作等へ一律に強制せず、適用しない場合は理由と代替確認を作業前に示す。TDDで意図した初期の失敗は正式な不合格回数へ加算しない。
- レビューの指摘を取り下げるときは、該当する仕様・コードの位置・再現結果やテスト出力を根拠として残す。「問題ないはず」など証拠のない反証を認めない。検証担当には指摘が正しいかを中立に確認させ、反証する結論へ誘導しない。報告した担当の人数だけで採否を決めず、判断できない指摘は未確認として履歴に残し、影響と次の確認を示す。必須条件に関わる未確認を残したまま合格にしない。

## 記録・完了・再開

- 各機能の実装・修正・拡張が終わるたびに、変更した実物と承認済み資料を照合する。機能・振る舞い・完成条件・技術上の規律が承認を経て変わった場合はREQUIREMENTS.md、表示・文言・操作が変わった場合は該当する画面仕様と共通UIルール、確認方法や期待結果が変わった場合はテストとCHECKS.mdを更新する。AGENTS.mdは参照先または全作業に共通する指示が変わった場合に更新し、機能の詳細は書き足さない。判断と結果はTASKS.mdへ残す。該当しない資料は理由を確認し、機械的に全ファイルを書き換えない。
- 資料を実装へ無条件に合わせない。差異があれば、承認済み仕様に対する実装の誤り、承認された仕様変更、未決定事項に分ける。誤りは実装を直し、仕様変更は承認内容を正式な資料へ反映してから確認条件・テスト・影響箇所を再検証する。未決定の変更を実装済みという理由で正当化しない。
- 各タスクの完了前に、対象の要件ID・画面ID・確認条件IDと変更したコード・実画面・テスト結果・資料の対応を確認する。古い参照先、重複した仕様、未反映の承認済み変更を残さず、資料更新の有無と理由をTASKS.mdに記録する。必要な整合確認が未実施なら完了扱いにしない。
- 要件承認前の決定・未決定・調査とレビューの結果・不合格履歴はREQUIREMENTS.mdへ記録する。その作成前はチャットに残し、作成時に転記する。要件承認後にTASKS.mdを作り、進捗と評価履歴を引き継ぐ。以後は開始・評価・修正・停止・完了時に更新する。HTMLボードを作る場合はTASKS.mdから生成し、二重管理しない。
- 記録・引き継ぎには、その工程で作成済みかつ該当する資料・IDを使用する。未作成のものは未作成と明記し、必要な決定・評価履歴はチャットに残す。資料作成時に転記する。
- 要件ID、画面ID、タスクID、確認条件IDは、作成済みかつ該当するものを対象版・結果・証拠と結び付ける。読めないリンクや古い証拠で合格にしない。
- 変更内容、実行した検証と結果、未解決事項、未実施理由、残る影響、次のタスクを報告する。
- 端末・OS・ブラウザ・version・build・commit、配布した場合のBuild IDやUpdate ID、ユーザーの受入結果を該当範囲で残す。
- レビュー合格、全体の確認、ユーザー受入、公開承認を区別する。未実装、不採用、延期、未確認を完了へ混ぜない。
- 中断時は、TASKS.mdの現在位置、対象タスクの履歴、中断・再開メモを更新する。要件承認前の中断・再開記録はREQUIREMENTS.mdへ、その作成前はチャットへ残す。要件承認後でもTASKS.mdが未作成の場合はチャットに残し、作成時に転記する。未完了の変更を完了扱いにしない。
- 再開時は、対象タスク、承認範囲、未決定、不合格回数、直近の証拠を読み、実際の作業場所・コード・変更履歴と照合する。過去チャットを知っている前提で進めない。
- 実行できるアプリがある場合は、CHECKS.mdで定めた起動確認と主要操作の短い試験を、新しい実装の前に行う。
- 記録と実物が異なる場合や、基本動作が失敗する場合は、原因と影響を整理する。承認範囲内で修復できるものは修復・再検証し、範囲外または判断が必要なものは該当作業を止めて報告する。
- 中断した処理は、すでに完了していないかを確認してから再実行する。外部送信・ビルド・データ変更などを、状態不明のまま重複実行しない。
- 要件確定時、実装開始前、公開前にAGENTS.mdの参照案内と、変更に関係するWORKFLOW.md・要件・確認方法を見直す。旧仕様と矛盾する指示を残さない。更新後は各担当に読み直させ、適用内容を確認する。

## 工程ごとの進行

- ユーザーが今回依頼した工程と承認範囲を確認して作業する。次工程が、ユーザーから明示的に実行を依頼された範囲に含まれている場合は、前提条件と合格条件を満たしたうえで継続する。含まれていない場合は依頼を待つ。計画の承認だけを、全工程の実行依頼と扱わない。
- 要件承認後に、承認済み要件とユーザーから渡された確認内容をTASKS.mdの作業と確認条件へ整理する。資料に項目が書かれているだけで実施済みと扱わない。
- 「対象外」は理由・判定者・確認日を残す。未実装や後回しを対象外へ置き換えない。「未確認」は合格にしない。
- 判定は合格／不合格／未確認／対象外。該当する必須項目がすべて合格し、必要なユーザー承認が得られ、次工程が明示的に実行を依頼された範囲に含まれている場合に次へ進む。
- 今回依頼された工程の範囲を守る。追加判断が必要なら理由と影響を示す。承認済み判断を毎工程で最初から聞き直さない。
- 確認項目には、作成済みかつ該当する要件ID・条件ID・タスクIDを付け、対象版・証拠と結び付ける。未作成の資料・IDは「記録・完了・再開」の扱いに従う。実装後に条件を合わせて書き換えない。
- 独立した調査や契約待ちは並行できるが、必須の前提が未完了の工程へ進まない。準備開始時期と完了期限はTASKS.mdで管理する。未作成の場合は「記録・完了・再開」の記録先に従い、作成時に転記する。
- 工数は対象・規模・使える時間を確認して見積もる。過去の別アプリの開発期間を共通の保証にしない。
- 承認済みの確認内容で扱えていない高リスク領域・配布形態・連携が見つかったら報告し、追加調査の適用条件と公式根拠を確認する。曖昧なまま公開へ進まない。
- 各工程で、具体作業、成果物、担当、使うスキルと理由、変更しない範囲、承認地点、確認方法と合格条件、次へ進む条件を確認する。特定のスキルを使っただけで完了にしない。

## 外部操作を行う場合

- 外部へのデータ・コード送信は送信先・内容・目的を説明し承認を得る。送信先や情報の種類が変わる場合は再確認する。
- 実際のAPIへリクエストを送るテストは、実行前に接続先・操作内容・送信データ・費用やデータ変更の有無を説明し、「AIが実行してよいか、ユーザー自身が実行するか」を必ず質問する。回答を得るまで実行しない。一般的な実装・テストの依頼を、この許可の代わりにしない。許可は説明した範囲に限り、範囲が変わる場合は再確認する。実際のAPIへ通信しない模擬テスト（本物のサービスの代わりに、用意した返事を返すテスト）は、この確認の対象外とする。
- 契約、課金、有料サービスの有効化は料金条件と利用上限を示す。
- 削除、上書きによる消失、履歴変更、環境初期化は対象と復元可否を説明する。承認済みの通常編集に含まれる文章置換は再承認不要。

## データ・認証情報を扱う場合

- 個人情報・健康情報は必要性と利用範囲を確認し、不要な収集・保存・外部送信をしない。テスト・スクリーンショットには架空データを使う。
- APIキー、パスワード等の認証情報をチャットへの貼り付けで求めない。利用環境に合う設定方法を案内する。
- 秘密値をコード、ログ、スクリーンショット、共有資料、Git履歴へ含めない。確認時にも値を表示しない。
- 秘密入り.env等をGit管理から除外し、設定例にはダミー値のみを記載する。VITE_等の公開用環境変数に秘密を入れない。除外設定だけで過去の履歴や生成物が安全と判断しない。
