# UI共通ルール

## 保存先と資料の役割

- UI共通の判断は本書を正式な保存先とする。個別の表示・操作・状態・遷移は `docs/ui/screens/<画面名>.md` を正式な保存先とする。同じ画面の仕様を別の場所で並行管理しない。
- `docs/REQUIREMENTS.md` は製品要件、個別回答、承認経緯と完成条件の記録として維持する。`docs/TASKS.md` は作業状態、評価と修正の履歴を記録する。画面仕様は両資料の根拠を参照し、既存の承認履歴を移動・削除しない。
- 現在の個別資料は `docs/ui/screens/受付・対象確認.md` のみ。これは要件にある「ログの受付・対象確認」の役割を受ける資料であり、独立した1画面にする決定ではない。進捗一覧、件ごとの確認、レビューの個別資料は未作成。画面数と役割の分け方は T-005 で決める。

## 仕様に従う範囲

- 画面の文言、見出し、機能、ボタン、入力、操作、状態、遷移は、該当する要件と承認済みの画面仕様に従う。仕様にない説明文・見出し・ボタン・機能を独断で追加しない。画像だけを根拠に機能や文言を補わない。
- 文言が動的に変わる場合は、表示元と表示条件を個別の画面仕様で定める。未決定の文言を完成文言として扱わない。
- 要件・共通ルール・画面仕様・画像が食い違うときは、出典と承認状況を照合し、製品判断が必要なら決定を記録してから仕様を更新する。

## 固定する内容と改善できる内容

- **固定**：要件と個別回答で決まった目的、対象・対象外、文言、機能、操作順序、状態の意味、完成条件。変更には内容と影響の確認、ユーザーの承認が必要。
- **改善可能**：画面仕様で調整を認めた余白、整列、文字の読みやすさなど、固定内容と利用者の操作を変えない見た目。対象画面の設計・受入時に確認する。画面数、配置、遷移、未決定の表示文言は、現時点で「改善可能」として自由に決められる項目ではなく、T-005 の設計事項。
- 画面の受入後は、別の機能変更に無関係な任意の見た目の改善を混ぜない。仕様違反の修正とデザイン改善を分けて記録する。

## 承認後の変更と画像

- 承認済みの画面仕様を変える際は、変更理由、対象画面、変更前後の文言・操作・状態、影響する要件・完成条件・テストを示し、承認内容を個別資料と `docs/TASKS.md` の履歴に残す。承認前の案と承認済み内容を区別し、過去の判断を消さない。
- 参考画像は設計の出発点。ユーザーが受け入れた実装画面の画像を回帰確認用の**基準画像**とする。基準画像には対象版、画面、状態、表示条件、承認時点を結び付ける。
- 基準画像はテストを通すために自動更新しない。承認された画面変更と実画面の検証結果を確認した後に更新し、変更前の基準と承認履歴を追跡できるようにする。画像比較だけで操作や保存の合格としない。
- 参考画像、基準画像、対応テストの参照先は、実物を作成して確認した時点で個別の画面仕様に追加する。現在はいずれも未作成。空ファイルや参照予定だけで準備済みとしない。

## 作業時の確認

- 画面を設計・変更する前に、対象の個別資料、そこに記載した出典、作成済みの参考画像・基準画像・対応テストを読む。未作成のものは未作成と記録する。
- UI変更後は実画面の文言、不要な表示、重なり・欠け・はみ出し、操作を確認する。共通部品の変更が影響する画面も確認する。未実施は未確認として報告する。
