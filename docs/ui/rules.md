# UI共通ルール

## 保存先と資料の役割

- UI共通の判断は本書を正式な保存先とする。個別の表示・操作・状態・遷移は `docs/ui/screens/<画面名>.md` を正式な保存先とする。同じ画面の仕様を別の場所で並行管理しない。
- `docs/REQUIREMENTS.md` は製品要件、個別回答、承認経緯と完成条件の記録として維持する。`docs/TASKS.md` は作業状態、評価と修正の履歴を記録する。画面仕様は両資料の根拠を参照し、既存の承認履歴を移動・削除しない。
- 個別資料は `docs/ui/screens/受付・対象確認.md`、`docs/ui/screens/進捗一覧.md`、`docs/ui/screens/件ごとの確認.md`、`docs/ui/screens/レビュー.md` に置く。要件にある4つの役割をそれぞれ1画面に対応させる構成は、2026-09-24に**実装する画面設計として承認済み**。後続3画面の参考画像は未作成。

## 仕様に従う範囲

- 画面の文言、見出し、機能、ボタン、入力、操作、状態、遷移は、該当する要件と承認済みの画面仕様に従う。仕様にない説明文・見出し・ボタン・機能を独断で追加しない。画像だけを根拠に機能や文言を補わない。
- 文言が動的に変わる場合は、表示元と表示条件を個別の画面仕様で定める。未決定の文言を完成文言として扱わない。
- 要件・共通ルール・画面仕様・画像が食い違うときは、出典と承認状況を照合し、製品判断が必要なら決定を記録してから仕様を更新する。

### 画面仕様の表記と承認境界

- 各画面の `SCR-01` などは画面ID、`REQ-01` などは要件本文の主要操作ID、`C01` などは完成条件ID。設計承認は実装・検証・実物の受入を意味しない。
- 項目表では **要件確定**（承認済み要件に明記）、**設計承認済み**（2026-09-24にユーザーが承認した具体的な画面案）、**未決定**（具体値や動作の記載がなく調査・判断待ち）、**対象外**（理由付き）を区別する。承認前の提案・未承認という表記は承認履歴として残せるが、現行の実装指示と取り違えない。未決定の正確な文言、初期値、制限、条件、成功・失敗表示、遷移先は推測で埋めない。
- 「該当なし」は対象と理由を併記する。表示専用項目には操作・入力初期値がなく、ボタンには入力値の初期値がない。失敗しない静的表示には成功・失敗遷移がない。この区別を省略欄で隠さない。
- 動的な値は、表示元・表示形式・表示条件を個別資料に記す。ログなどの架空データの例は固定文言にしない。翻訳は承認済み要件にないため現時点では対象外とし、日本語以外の翻訳文言・言語切替を追加しない。将来採用するなら各文言の原文、翻訳元、表示条件と承認を別に定める。

## 固定する内容と改善できる内容

- **固定**：要件・個別回答と承認済みの個別画面仕様で決まった目的、対象・対象外、文言、機能、項目、操作の意味と順序、状態、遷移、完成条件。変更には理由と案・影響の提示、ユーザーの承認が必要。
- **改善可能**：画面仕様で調整を認めた余白、整列、文字の読みやすさなど、固定内容と利用者の操作を変えない見た目。画面数、承認済みの配置・遷移、未決定の表示文言は「改善可能」として自由に決められる項目ではない。
- 初回実装で調整できるのは、承認された画面の情報の順番と操作の意味を保つ範囲の余白、文字サイズ、行間、整列、境界線、色のコントラスト、画面幅に応じた欠け・重なりの防止。項目・ボタンの追加削除、正確な文言、入力制限、表示条件、状態名、操作結果、遷移の変更は見た目の調整に含めない。
- 画面の受入後は、別の機能変更に無関係な任意の見た目の改善を混ぜない。仕様違反の修正とデザイン改善を分けて記録する。

## 承認後の変更と画像

- 承認済みの画面仕様を変える必要がある場合は、変更理由と具体案、対象画面、変更前後の文言・機能・項目・操作の意味・状態・遷移、影響する要件・完成条件・テストを**変更前に**示す。承認後に個別資料と `docs/TASKS.md` の履歴へ反映し、過去の判断を消さない。
- 参考画像は設計の出発点。ユーザーが受け入れた実装画面の画像を回帰確認用の**基準画像**とする。基準画像には対象版、画面、状態、表示条件、承認時点を結び付ける。
- 基準画像はテストを通すために自動更新しない。承認された画面変更と実画面の検証結果を確認した後に更新し、変更前の基準と承認履歴を追跡できるようにする。画像比較だけで操作や保存の合格としない。
- 参考画像、基準画像、対応テストの参照先は、実物を作成して確認した時点で個別の画面仕様に追加する。空ファイルや参照予定だけで準備済みとしない。

## 作業時の確認

- 画面を設計・変更する前に、対象の個別資料、そこに記載した出典、作成済みの参考画像・基準画像・対応テストを読む。未作成のものは未作成と記録する。
- UI変更後は実画面の文言、不要な表示、重なり・欠け・はみ出し、操作を確認する。共通部品の変更が影響する画面も確認する。未実施は未確認として報告する。
- T-008・T-009（工程8・9）では実際の画面を表示し、承認済み文言との一致、仕様外の表示の有無、欠け・重なり、操作の意味と結果を確認してからユーザーへ提示する。設計承認と実装検証・実物受入は別に記録する。
