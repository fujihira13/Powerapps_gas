# MQ照合の2ファイル受付と1操作化：実装計画（承認済み）

作成日・ユーザー承認日: 2026-09-28。対象はDeveloper環境の非公開「架空ログ証跡アプリ」4画面、件表、既存の件別Excel転記フロー。**この文書は計画であり、クラウド反映・公開・実機試験の実施記録ではない。**

## 結論と変更境界

新規受付は「更新対象一覧（Excel）」1冊と「サーバーログ（txt）」1件を、それぞれ独立した欄で選ぶ。環境・サーバー・対象処理日を確認し、「照合を開始」を1回押す。内部では保存、件IDと2ファイルの読戻し、開始受付、フロー起動を順番に行う。重複ファイル名の警告を受けた場合だけ明示的な続行確認が入る。旧ログのみ件は表示を残し、再実行しない。4画面、担当者確認、レビュー、元の更新対象一覧ブックと既存結果ブックは残す。公開は含めない。

現行の`{Attachments}`欄は1件に対する単一の添付集合である。ラベルを2つにするだけでは独立した2つの選択欄にならない。標準のAttachmentsコントロールはフォーム内の添付列でのみアップロードできるため、**新しい子テーブルに役割別の2行を保存する方式**を採る。まず既存メタデータとStudioの利用可能な添付欄を読み取る。子テーブル作成後、実データを保存する前に2フォームの構文と入力保持を確認する。成立しなければアプリ・フロー更新と試験データ作成へ進まず、1欄への後退も無断で行わない。[Microsoft: Attachments control](https://learn.microsoft.com/en-us/power-apps/maker/canvas-apps/controls/control-attachments)

## 正確な画面動作

| 状態 | 利用者に見えるもの | 内部動作／安全条件 |
| --- | --- | --- |
| 入力前 | 「更新対象一覧（Excel）」「サーバーログ（txt）」の別欄、環境、サーバー、当日を初期値とする変更可能な対象処理日。「照合を開始」は無効 | `.xlsx`と`.txt`を各1件、形式外と同役割の複数添付を拒否する。実行回は入力しない |
| 入力完了 | 「照合を開始」が有効 | 同名ファイルの既存警告はファイル名による注意喚起であり、内容一致とは言わない。照会不能なら停止 |
| 開始操作後 | 「保存を確認しています」→「照合を開始しています」→進捗一覧。処理中は再押下不可 | 親件を作り、役割別の子2行と各添付を保存する。親GUID、環境、サーバー、日付、2子行の役割・名前・添付を読み戻した場合に限り、親状態を開始受付済みにして既存フローを1回起動する。`SubmitForm`は非同期なので、フォームのOnSuccessで次段へ進む |
| 保存失敗・読戻し不一致 | 件を成功表示せず、理由を示して要確認 | フローを起動しない。途中作成された親・子行を自動削除せず、同一操作を再送しない |
| 開始結果不明 | 「開始結果を確認できません。進捗一覧を確認してください」 | フローを再起動しない。既存の結果不明保全を維持 |

「保存」を画面からなくしても、証跡と担当者確認に必要な記録の保存は内部で行う。利用者は保存操作を別に行わない。

## データ・フロー・結果表示

| 対象 | 実装内容 | 既存データとの関係 |
| --- | --- | --- |
| Dataverse | 現行の件表に親子参照できる子テーブルを1つ追加。列は親件への参照、役割（Excel／ログ）、表示名、標準Attachments。新しい受付だけ各役割1行を作る。役割＋親件の一意性を設けるか、同等の二重作成防止を実装前にメタデータで確認する | 既存件表・Notes添付・結果Excelの値を変更しない。子行のない旧件は履歴閲覧のみ |
| Canvas Screen1 | 2つの独立したフォームの添付欄を置き、内部の親保存→子ログ保存→子Excel保存→読戻し→開始を1つの操作につなぐ。現行の「ログのみ」選択、「保存」「処理開始」の可視操作を新規受付から外す | 既存の同名警告、環境・サーバー・日付、保存失敗／結果不明停止を保つ |
| Canvas Screen2/3 | Screen2は件の進捗と差異件数だけを表示。Screen3の右側は欠落・予定外IDだけ表示し、正常ID行を隠す。差異0件かつ終了表示あり、入力と結果の読戻し完了時だけ「予定したIDはすべてログに記録されています」。欠落は「ログに記録されていないID」、予定外は「一覧にないIDがログにあります」。終了表示がない場合は、差異件数に関わらず「ログが最後まで出力されたことを確認できません」 | 旧ログのみ件は履歴として表示し、MQ比較済みとは見せない。担当者確認・レビューは維持 |
| フロー | 引数は従来どおり件GUID。新方式の件では子表を親GUIDで検索し、役割がExcel／ログの子を各1行に限定。各子GUIDに関連するNotes添付を1件ずつ読み、ファイル名・拡張子・内容を照合して既存のID比較・Excel生成・読戻しへ渡す。並び順で役割を判断しない。子行／Notesの片方欠落・複数・内容形式外は結果Excel作成前に停止 | 旧件は再起動しない。従来の親Notes参照定義は既存件の記録を壊さない範囲で保つ |
| 結果Excel | 元ブックには書き込まず、件GUIDの別の結果Excelを作る。`証跡`と`MQ_Comparison`の全明細を維持する。画面の右側だけ成功IDの行を隠す | 既存結果Excelを上書きしない。画面の「結果Excelを開く」は読戻し確認済みURLがある時だけ有効 |

画面の「すべてログに記録」は、ログの出力内容と更新対象一覧の一致を示す。サーバーへの反映成功を断定しない。`ALL SUCCESS`は終了行として検査し、長い注意文を画面の主結果から外す。終了行なしは一致表示にしない。

## 実装順と対象ファイル

1. Developer環境の対象アプリ・フロー・件表定義と子テーブル追加先ソリューションを読取り、退避する。Canvas MCPで現行6 YAMLを新規ディレクトリへ同期する。同期できない間はYAML編集を開始しない。既存の未追跡4パスは保持する。
2. 子テーブルのSchemaName、親Lookup、役割列、Notes関連付け、親Lookup＋役割の一意キーを確定する。子テーブル作成後、Canvasで独立フォーム2つの構文・入力保持を検証する。実現不能ならアプリ・フローの更新と試験データ作成前に停止する。追加済みテーブルは勝手に削除しない。
3. `Screen1.pa.yaml`を変更し、2フォームの非同期保存連鎖、読戻し、1回起動、同名警告、失敗保留を実装する。`App.pa.yaml`は新データソース結線が必要な場合のみ変更する。
4. `outputs/flow-implementation/`のフロー定義生成・検証を更新し、新旧入力の境界を明示する。結果画面の差異表示は`Screen2.pa.yaml`と`Screen3.pa.yaml`で変更する。`Screen4.pa.yaml`は表示連動が必要な場合のみ変更する。
5. `docs/REQUIREMENTS.md`、`docs/ui/screens/受付・対象確認.md`、`進捗一覧.md`、`件ごとの確認.md`、`docs/CHECKS.md`、`docs/TASKS.md`と利用手順を承認後の仕様に合わせる。旧「ログのみ」「保存→別操作で開始」は履歴として残し、現行仕様とは区別する。
6. ローカル検証後に非公開アプリとフローを更新し、差分を読戻す。新規架空データで最小1件の正常照合と1件の入力不足・同名警告を確認する。新規行・添付・結果Excelの上限はクラウド操作前に別途明示する。
