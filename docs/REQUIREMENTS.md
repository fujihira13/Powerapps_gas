# 要件定義

## 目的の整理

この節は、実務で起きたこと、転職活動で伝えたいこと、現時点で了承を得た試作の方向を整理する。

### この資料で扱う作品と、その背景

本作品は、転職活動で示すために検討しているポートフォリオである。題材は、ガス会社の基幹システムの運用・保守に、SES（外部企業の案件に技術者として参画する働き方）のチームの一員として携わった際の実務経験に基づく。

作品の出発点はガス会社での経験だが、特定のガス会社だけに使うアプリにはしない。複数の対象から取得したファイルを、決められた記録先へ反映し、作業状況を確認する運用作業として捉える。ほかの業界の運用チームにも通じる課題として説明できる作品を目指す。

作品の題材となる実務には、**定期的な処理の結果を記録し、担当者が確認して、レビュアーへ引き継ぐ業務**が含まれる。この実務に基づく課題から小さな改善を考え、その改善が担う範囲と残る課題を説明できるポートフォリオにする。レビュー工程を作品の機能に含めるかは、まだ決めていない。営業・経理など別の職種向けの業務を、実体験として作り替える意図ではない。

同じ職場で行った管理表の更新準備の自動化と、顧客から依頼された既存マクロの不具合改修は、このログ転記とは別の作業である。職務経歴書で述べている「1回あたり約1時間の短縮」は別の手順簡略化による成果であり、このログ転記の効果として使わない。

### 誰が、どの場面で、何に困っていたか

- **作業担当者：** バッチ処理後にログを取得し、証跡用Excelへの転記と処理結果の確認を行い、完了を報告する人。ユーザー自身がこの役割を担当した。
- **レビュアー：** 完了報告を受け、転記されたログやExcelの結果を確認し直す人。ユーザー自身も、別の作業ではレビュアーを担当することがあった。役割は人に固定されていない。
- **困る場面：** 複数の環境・サーバーのログを扱い、今回の処理に対応する証跡用Excelを準備して転記し、結果を確認してレビューに渡すまでの一連の作業。転記後も、正しいログが貼られたか、Excelの関数を使って結果を読めるかを人が確かめる必要があった。

この作品で示したい課題は、今回の処理に対応する証跡を準備・転記し、結果を確認してレビューへ渡すまでに、手間や誤認が生じていたことである。**最初の試作で取り組む目的は、取得済みログを証跡用Excelへ転記する定型作業の負担を減らし、環境・サーバーごとの転記とExcelへの反映状況を確認しやすくすること**である。これは先方が了承した小さな試作の方向に対応する。一連の作業全体に残っていた問題も背景として示すが、試作だけで解決したとは扱わない。

### 題材にする実務の流れ

運用・保守チームでは、次の作業を行っていた。

- テスト環境でバッチ処理（決められた処理をまとめて実行する作業）を実行する。
- 実行後、複数のサーバーから、処理結果を記録したログを取得する。
- 取得したログを、それぞれ対応する証跡用Excelへ貼り付ける。証跡用Excelは、作業結果を記録し、確認するためのファイルである。
- 転記後、Excelに元からある関数を使い、処理結果に問題がないかを人が確認する。
- 作業担当者が完了を報告した後、レビュアーが再確認する。実務ではログをもう一度貼り直して確認したり、Excelの関数に「不合格」が出ていないか確認したりしていた。ユーザー自身がレビューする際にも、貼り直して結果を確認していた。

ログを貼り付ける前には、取得したログを指定のフォルダーに置く作業があった。また、指定の証跡用Excelは、元からある関数を残したまま前回のログ内容を初期化し、今回のログを読み込める状態にする必要があった。ここでいう「作り直す」は、関数を一から作成し直す意味ではない。

取得済みのログを証跡用Excelへ貼り付ける作業は、手作業で繰り返していた。このSESチーム内の定型作業に自ら着目し、Excel VBAのマクロ（Excel上の操作を自動化するプログラム）を作成した。マクロで自動化した範囲は、**取得済みログを対応する証跡用Excelへ転記する部分**である。サーバーからのログ取得、バッチ処理の実行、処理結果の最終確認をマクロが代行したという意味ではない。

### 実務で残っていた負担と、起きた問題

- VBAで転記を自動化した後も、ログを指定のフォルダーに置き、証跡用Excelの前回分の内容を初期化する準備には手間がかかった。
- ログが正しく貼り付けられていないと、Excelの関数を期待どおりに使えなかった。関数自体に不具合がある場合もあり、結果の確認が必要だった。関数の結果だけでは、どこに問題があるか分かりにくいこともあった。
- 過去のログを今回の証跡に貼り付けたことがあった。ログが何らかの影響で更新されず、過去のログは「問題なし」だったため、今回の処理も問題ないと判断してしまった。しかし、その時点では今回のログを確認できていなかった。後に上司がログ本文を確認し、本文に記載された日付が当日ではなく過去の日付だったことで気づいた。ログが更新されなかった原因と、今回のバッチ処理の実際の成否は、この話からは分からない。
- レビュアーが貼り直して再確認する作業もあった。転記の自動化後も、人による結果確認とレビューは残っていた。

古いログの例は、**Excel上で「問題なし」と見えることと、今回の処理結果を正しく確認できたことは同じではない**と示している。ただし、当時のVBAや今後の試作が、古いログの使用を自動で発見・防止できたと説明しない。

### ポートフォリオで示したいこと

転職活動では、現場の定型作業を理解し、手作業の課題を整理して、実際に使える仕組みに変える力を示したい。特に、志望するFDE（顧客の現場で課題を理解し、解決策の設計・実装に関わるエンジニア）に向けて、実務で何を見つけ、どこを改善し、作品ではそれをどう再現したかを説明できるようにする。

最初に扱う題材は、取得済みの実行ログを証跡用Excelへ転記する作業である。実務で行ったことと、ポートフォリオで新たに作る機能を区別する。ほかの業界への応用可能性を示す際も、営業・経理など別の部門で同じ転記処理をそのまま使えるとは説明しない。

作品を見せる際は、少なくとも「実際の作業と役割」「起きていた負担や誤認」「試作で改善した範囲」「まだ人が確認する範囲」を一続きで説明できるようにする。これにより、単にツールを作ったことだけでなく、現場の作業を理解し、問題を正確に捉え、解決範囲を見極める姿勢を示す。効果の数値や、実務で起きなかった機能・成果は根拠なく加えない。

他業界への応用は、**定期的な処理の結果を記録し、担当者とレビュアーが確認する**という共通の業務の形として説明する。業界が違えば、扱うファイル、確認の基準、レビューの手順は異なる。別業界でも同じ製品がそのまま使えることや、営業・経理の現場で需要が確認済みであることは、現時点では主張しない。

### 転職活動の相談相手に伝え、了承を得た試作の方向

転職活動の相談相手に、次の方向を提案し、了承を得た。

- 取得済みの実行ログを証跡用Excelへ転記する作業を、Power Automate（定型処理を自動で進めるMicrosoftのサービス）で小さく再現する。
- Power Apps（業務用の操作・確認画面を作るMicrosoftのサービス）では、環境・サーバーごとにログの転記が完了したか、証跡用Excelに反映されたかを一覧で確認できる画面を考える。

了承されたのは、この試作の方向である。詳細仕様、実装方法、完成条件、公開まで承認されたわけではない。

### 試作の範囲と、まだ決めていないこと

先方から方向性について了承を得た小さな試作は、取得済みログの証跡用Excelへの転記と、環境・サーバーごとの転記・反映状況を一覧で確認する画面の検討である。**バッチ処理の成否をアプリが自動判定すること、古いログを自動検出すること、Excelの関数の不具合を自動修正することは、了承済みの機能ではない。** 転記や一覧表示だけで、古いログの誤使用や結果確認の問題まで解消できたと説明しない。

次の点は、実務上の課題または作品で扱う可能性として整理し、機能・完成条件としてはまだ決めない。

- 指定フォルダーへの配置や、証跡用Excelの初期化を作品の範囲に含めるか。
- 過去のログの誤使用を作品で扱うか、扱うならどこまで支援するか。実務で上司が見たのはファイルの更新日時ではなく、**ログ本文に記載された日付**である。
- 関数が使えない・「不合格」が出たとき、どこまで原因を分かりやすく示すか。
- レビュアーへの完了報告と再確認の状況を、作品の中でどこまで扱うか。
- デモで使う架空データ、他業界への説明例、完成条件と効果の確かめ方。
- 元のログと証跡用Excelの具体的な形式、作品を動かす環境。実務のログ、顧客情報、既存の証跡用Excelを作品や公開物に持ち込むことは承認されていない。加工・匿名化した情報を使う場合も、利用する内容と公開範囲は別途確認する。

これらを決める際は、実務で確認した事実と作品として新たに提案する内容を区別し、ユーザーと認識を合わせる。
